# Автоматическая обработка очереди заявок в n8n

Проект автоматизирует обработку новых клиентских заявок из NocoDB.

Основной workflow запускается по расписанию, получает необработанные
заявки, передаёт каждую запись в отдельный подсценарий, обрабатывает
текст заявки через ИИ и сохраняет результат в журнал.

После успешной обработки исходная заявка получает статус
`обработан`.

## Цель проекта

Автоматизировать регулярную обработку очереди заявок без ручного
запуска сценария.

Проект демонстрирует:

- работу с Schedule Trigger;
- получение данных из NocoDB;
- фильтрацию записей;
- обработку нескольких items;
- использование Subworkflow;
- передачу Input Parameters;
- подключение OpenRouter через HTTP Request;
- разбор JSON-ответа ИИ;
- создание и обновление строк в NocoDB;
- просмотр основного Execution и Sub Execution.

## Архитектура

Основной сценарий:

Schedule Trigger
→ Search rows
→ Call Process_single_request

Подсценарий:

Start
→ HTTP Request
→ Code in JavaScript
→ Create a row
→ Update a row

## Основной workflow

Основной сценарий называется:

`NocoDB Queue — Scheduled Runner`

Он запускается каждые 5 минут.

### Schedule Trigger

Настройка:

- интервал: 5 минут;
- часовой пояс: Europe/Moscow.

### Search rows

Нода получает записи из таблицы `Входящие`.

Фильтр:

`status = новый`

Формула NocoDB:

`(status,eq,новый)`

Включён параметр `Return All`, поэтому сценарий получает все новые
заявки.

### Call Process_single_request

Каждая найденная строка передаётся в подсценарий.

Передаваемые параметры:

- `source_id`;
- `name`;
- `email`;
- `request`.

## Подсценарий

Подсценарий называется:

`Process_single_request`

Он отвечает за обработку одной заявки.

### Input Parameters

Подсценарий получает:

| Поле | Тип | Назначение |
|---|---|---|
| source_id | Number | ID исходной строки NocoDB |
| name | String | Имя клиента |
| email | String | Электронная почта |
| request | String | Текст заявки |

### HTTP Request

Текст заявки отправляется в OpenRouter через OpenAI-совместимый API.

Используемая модель:

`deepseek/deepseek-chat`

ИИ должен вернуть JSON:

```json
{
  "summary": "краткое содержание заявки",
  "direction": "направление заявки"
}

### Code in JavaScript

Code-нода удаляет Markdown-обёртку из ответа ИИ и преобразует строку
в JSON.

На выходе формируется структура:
{
  "source_id": 1,
  "summary": "Автоматизация обработки заявок",
  "direction": "Интеграция"
}
### Create a row

Результат записывается в таблицу Обработанные.

Заполняются поля:

"source_id";
"summary";
"direction".

### Update a row

После успешной записи исходная заявка обновляется в таблице
Входящие.

Поле:

status = обработан

Для обновления используется source_id, переданный из основного
workflow.

### Структура NocoDB

Таблица Входящие

Поле	Тип
"name"	    Single line text
"email"	    Email
"request"	Long text
"status"	Single select
Значения поля status:
. новый;
. обработан.

Таблица Обработанные

Поле	Тип
"source_id"	Number
"summary"	Long text
"direction"	Single line text

Логика работы

1. Schedule Trigger запускает основной workflow каждые 5 минут.
2. NocoDB возвращает все строки со статусом новый.
3. Каждая заявка передаётся в подсценарий.
4. OpenRouter анализирует поле request.
5. Code-нода разбирает JSON-ответ.
6. Результат сохраняется в таблице Обработанные.
7. Исходная запись получает статус обработан.
8. При следующем запуске эта запись больше не выбирается.
9. Защита от повторной обработки

. Основной workflow получает только строки:
status = новый
. После обработки статус меняется на:
обработан
. Поэтому одна заявка не должна повторно отправляться в ИИ.

Проверенные случаи

. Есть новые заявки
. записи найдены;
. для каждой заявки запущен отдельный Sub Execution;
. результат записан в Обработанные;
. статус изменён на обработан.
. Новых заявок нет
. Нода Search rows возвращает 0 items.
. Выполнение останавливается, и пустые записи не создаются.

## OpenRouter Credentials / Учётные данные OpenRouter

Экспортированный workflow не содержит настоящего API-ключа. В заголовке `Authorization` используется безопасная заглушка `Bearer YOUR_OPENROUTER_API_KEY`.

Перед запуском проекта:

1. создайте в n8n credential типа `OpenRouter API`;
2. в ноде `HTTP Request` выберите `Authentication` → `Predefined Credential Type`;
3. выберите созданный credential `OpenRouter API`;
4. удалите ручной заголовок `Authorization` с заглушкой.

Настоящие API-ключи нельзя хранить в workflow, README или Git-репозитории.
